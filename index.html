반복 VOC를 고객 여정의 막힘으로 보고,
운영 프로세스와 서비스 개선으로 연결하는 사람

CX는 고객 접점에서 발견한 문제를 주문·배송·이벤트 운영 구조로 바꾸는 일이라고 생각합니다. 고객 화면만 바꾸는 일이 아니라, 주문 이후 데이터가 어떤 상태로 남고, 어떤 운영지표로 확인되며, 어떤 기준으로 고객에게 안내되는지까지 설계하는 일이라고 봅니다.

저는 반복 문의를 단순 처리로 끝내지 않고, 고객이 배송·미출고·품절·환불·교환·프로모션 단계에서 어느 시점에 오인하고 내부 처리가 어디서 다시 확인되는지 먼저 봅니다. 배송 제약 VOC는 UX 개선안으로, 환불·교환 문의는 의도 선택값 구조로 연결해왔고, 프로모션이나 운영 변경이 있을 때 반복적으로 발생할 수 있는 문의 유형을 미리 정리하고, 고객 안내 기준과 내부 처리 흐름을 구조화해 운영 부담을 줄이는 방식에도 익숙합니다.

초록마을에서는 B2C 고객 VOC를 제품·운영 개선 과제로 연결했고, 카카오VX에서는 제휴사별로 상이하던 예약·취소·위약 정보를 공통 확인 항목 중심으로 구조화해 상담 판단 기준으로 정리했습니다. 처음 접하는 도메인도 빠르게 구조화해 고객과 담당자가 이해할 수 있는 운영 언어로 바꾸는 것이 제 강점입니다.

고객·파트너 운영 기준 설계 VOC → 운영/서비스 개선 도메인 지식 번역 AI 실무 활용 Knowledge Base 구축 데이터 기반 문제 해결

Case 01

배송 제약 VOC를 상품별 안내 MVP로 전환 — 개선안 제안 · 당일 반영 · 반복 문의 0건 수준

Problem

배송 가능일이 다른 상품이 장바구니에 함께 담기면 주문이 차단됐지만, 고객에게는 일반적인 품절 안내가 노출돼 실제 원인을 알기 어려웠습니다.

이 문제는 과거에도 확인됐지만, 매장별 재고와 배송 방식, 여러 상품의 배송 가능일을 모두 계산해 정확한 충돌 원인을 안내하는 방식은 구현 범위가 커 실제 개선까지 이어지지 못했습니다.

이후 화요일에만 도착 가능한 신규 상품이 운영되자 동일 유형 문의가 짧은 시간에 6~10건 집중 발생했습니다. 고객은 실제 품절이 아닌데도 주문을 진행할 수 없어 시스템 오류로 인식하고 있었습니다.

핵심 문제는 고객의 이해 부족이 아니라, 주문이 막히는 시점에 어떤 상품 때문에 제한되는지 시스템이 설명하지 못하는 UX 구조에 있었습니다.

A 전면 개편 대신 상품별 안내 MVP 제안

문의 내용과 장바구니 구성, 실제 재고, 상품별 배송 조건을 확인해 실제 품절이 아니라 배송 가능일 충돌 문제로 원인을 정리했습니다.

모든 상품 조합의 충돌 원인을 자동으로 계산하는 전면 개편 대신, 배송 제약 상품 옆에 배송 가능 요일과 해결 방법을 보여주는 최소 개선안을 제안했습니다.

⚠️ 화요일에만 도착 가능한 상품이에요. 나누어 주문이 필요할 수 있어요.

기존 장바구니의 상품별 subtext 영역을 활용해, 고객이 주문 화면에서 다음 내용을 바로 확인할 수 있도록 했습니다.

· 어떤 상품 때문에 주문 가능일이 제한되는지
· 상품을 나누어 주문하면 해결될 수 있는지

개발팀에서 기존 subtext 영역을 활용할 수 있음을 확인했고, 개선안은 당일 장바구니 화면에 반영됐습니다.

B 유사 배송 제약 상품으로 확장

초기 화요일 도착 전용 상품에 반영한 뒤, 같은 조건의 다른 상품에도 동일한 안내를 적용했습니다.

이후 토요일에만 도착 가능한 상품이 추가됐을 때도 같은 구조를 활용해, 상품별 배송 가능 요일과 분리 주문 필요 가능성을 장바구니에서 확인할 수 있도록 확장했습니다.

Result

고객에게 일반 품절처럼 보이던 문제를, 상품별 배송 조건과 해결 행동을 장바구니에서 확인할 수 있는 구조로 바꿨습니다.

상담을 통해서만 설명할 수 있었던 정보를 고객이 주문 과정에서 직접 확인하도록 했으며, 첫 상품에 적용한 안내 방식은 다른 배송 제약 상품에도 확장됐습니다.

신규 상품 운영 직후 동일 문의 6~10건 집중 → 당일 반영 후 확인 기간 0건 수준

Insight

· 고객은 주문이 막혔다는 사실보다 왜 막혔고 무엇을 해야 하는지 알 수 없을 때 시스템 오류로 인식합니다.

· 전체 로직을 한 번에 바꾸기 어렵더라도, 고객이 막히는 화면에 원인과 다음 행동을 안내하면 실질적인 불편을 줄일 수 있습니다.

· 고객 접점의 반복 문의를 화면 개선으로 연결하면 상담 처리량을 줄이는 데서 끝나지 않고, 같은 문제의 재발 자체를 줄일 수 있습니다.

Case 02

고객 의도 기반 환불·교환 입력 구조 재설계 — 재확인 왕복 감소

Problem

환불·교환 등 고객이 원하는 해결방법이 별도 선택값으로 분리되어 있지 않아, 자유 텍스트 안에서 고객 의도를 다시 확인해야 하는 구조였습니다.

고객 의사 확인 없이 임의 처리할 경우 분쟁 리스크가 있어, 문의 접수 단계에서 고객이 원하는 해결방법을 먼저 선택하도록 하는 구조가 필요했습니다.

A 1:1 문의 접수 단계에서 기존 환불·교환 필드를 필수 선택값으로 전환

1:1 문의 등록 단계에서 기존 환불·교환 필드를 필수 선택값으로 쓰도록 제안해, 별도 기능을 새로 만들지 않고 고객이 문의 작성 시 환불/교환 의사를 먼저 선택하도록 하고, 해당 값이 CRM의 해결방법 필드로 노출되도록 개선안을 정리했습니다.

B 기존 CRM 영역 활용 · 개발 범위 최소화

답변 작성일과 중복되는 '확인일시' 영역을 '해결방법' 필드로 대체하는 방향을 제안해, 별도 개발 범위를 늘리지 않고 구조 변경이 가능한 지점을 확인했습니다.

Result

고객 의도 확인을 위한 추가 답변 왕복을 줄이고, 담당자가 문의 접수 단계에서 해결방법 선택값을 바로 확인할 수 있어 후속 처리 기준이 더 명확해졌습니다.

1:1 문의 단계에서 기존 환불·교환 필드를 필수 선택값으로 바꾸고, 해당 선택값이 CRM에서 바로 확인되도록 연동했습니다. 이를 통해 환불·재배송 의사를 다시 확인하는 왕복 과정을 줄이고 임의 처리 가능성을 낮췄습니다. (실제 시스템 화면이 아닌 개선 로직을 보여주기 위한 모형입니다.)

Insight

· 응대 단계에서 발생하는 재확인 비용은 대부분 입력 단계의 구조 문제에서 시작됩니다.

· 자유 텍스트는 유연해 보이지만, 실제로는 의도를 흐리는 구조입니다.

· 큰 개발 변경 없이 기존 필드 활용 방식만 다시 설계해도 운영 비용을 빠르게 줄일 수 있습니다.

Case 03

제휴사별 상이한 정책 정보 구조화 — 동일한 순서로 찾고 판단할 수 있도록

Problem

골프장 400여 곳의 예약·취소·위약 기준이 제휴사별로 다르게 관리되고 있었습니다. 어드민에 데이터는 있었지만, 골프장마다 정책의 표현 방식과 정보 배열 순서가 달라 담당자가 필요한 정보를 빠르게 찾기 어려운 구조였습니다.

예를 들어 어떤 골프장은 위약 기간 내 취소 시 예약만 제한되는지, 동반자로도 방문이 제한되는지까지 명확히 적혀 있었지만, 어떤 골프장은 표현이 모호했습니다. 위약금 입금 계좌, 예약실 전화번호, 운영시간, 취소 가능 기한 같은 핵심 정보도 골프장마다 위치가 달라, 동일한 문의를 처리할 때마다 전체 정책 문구를 다시 훑어야 했습니다.

그 결과 담당자별로 확인 속도와 해석 방식에 차이가 생겼고, 신규 인력이 정책을 익히는 데도 시간이 걸렸습니다.

A 400여 개 제휴사 정책 정보 구조 표준화

400여 개 제휴 골프장의 정책을 전수 확인하고, 담당자가 실제 문의 처리 시 먼저 확인해야 하는 순서대로 정보 구조를 재정리했습니다.

예약실 전화번호와 운영시간, 취소 가능 기한, 위약 적용 범위, 위약금 및 입금 계좌, 동반자 제한 여부, 예외 기준처럼 자주 확인하는 항목을 공통 구조로 정렬했습니다. 제휴사마다 다르게 쓰이던 표현도 동일한 기준으로 바꿔, 담당자가 같은 위치에서 같은 유형의 정보를 확인할 수 있도록 정리했습니다.

B 취소·위약·동반자 변경 기준 재정리

단순히 정보를 옮겨 적는 것이 아니라, 반복 문의가 발생하는 기준을 중심으로 정책을 다시 분류했습니다. 특히 위약 기간 내 취소 시 이후 예약만 제한되는지, 동반자 방문까지 제한되는지처럼 고객 안내에 영향을 주는 항목을 별도 기준으로 정리했습니다.

이를 통해 담당자가 전체 위약 규정을 매번 처음부터 읽지 않아도, 필요한 판단 항목을 빠르게 확인할 수 있도록 운영 가이드와 Knowledge Base를 재정비했습니다.

C 정책 최신화 및 온보딩 기준 정비

정책 변경이 발생할 때는 어드민과 내부 문서의 반영 위치가 달라지지 않도록 공유 흐름을 정리했습니다. 신규 인력에게도 동일한 순서와 표현 기준으로 안내할 수 있도록 온보딩 자료에 반영해, 개인 숙련도에 따라 판단이 달라지는 상황을 줄이고자 했습니다.

Result

제휴사별로 흩어져 있던 정책 정보가 공통 순서와 표현 기준으로 정리되면서, 담당자가 필요한 정보를 더 빠르게 찾고 동일한 방식으로 판단할 수 있는 기반이 마련되었습니다.

· 흩어진 정보는 자동으로 기준이 되지 않습니다. 실제 처리 순서에 맞게 재배열되어야 운영 기준이 됩니다.

· 정책 표준화는 내용을 하나로 통일하는 일이 아니라, 서로 다른 정책을 같은 방식으로 찾고 판단할 수 있게 만드는 일입니다.

· 파트너 운영에서 중요한 것은 모든 제휴사를 같게 만드는 것이 아니라, 다른 정책도 동일한 구조로 이해할 수 있게 만드는 것입니다.

Case 04

외부 물류 파트너 사고·배상 기준 재정의 — 배상 회수액 약 14.7배 증가

Problem

배송 사고가 발생했을 때 택배사와 외부 물류 운영사, 즉 3PL 파트너의 사고 확인 흐름, 증빙 기준, 비용 반영 기준이 각각 달라 배상 회수와 후속 처리가 지연되는 문제가 있었습니다.

택배사 사고 처리에서는 회수 필수, 송장 사진·외부 박스 사진·내품 사진 등 3종 증빙 요구로 인해 고객 응대 현장에서 자료 확보가 어려웠습니다. 주말 이후 접수된 건은 이미 상품이 폐기된 경우가 있었고, 유리병·간장류처럼 파손 시 안전 문제가 있는 상품은 고객에게 내품 사진을 다시 요청하기 어려웠습니다. 이로 인해 실제 사고가 확인된 건도 배상 처리로 이어지기 어려웠고, 배상 회수액은 월 50만 원 수준에 머물러 있었습니다.

이후 물류 운영사 전환 초기에는 오피킹, 출고누락, 포장불량, 파손 등 파트너 귀책 가능성이 있는 사고가 반복됐습니다. 그러나 전환 초기라 사고 확인, 책임 판단, 비용 반영 기준이 안정적으로 자리 잡지 못한 상태였고, 파트너 회신이 늦어지면 고객 환불·재배송·CS 보상 비용이 내부 부담으로 남는 구조였습니다.

A 택배 표준약관 근거 제시 · 회수·사진 증빙 기준 간소화

택배사 파손 사고 처리의 병목은 회수와 고객 증빙 기준이었습니다. 저는 단순히 회수 기준 완화를 요청하기보다, 택배 표준약관상 운송 중 포장 훼손이나 사고 인지 시 송화인에게 통보하고 조치해야 한다는 점에 주목했습니다.

파손 스캔이나 운송 중 훼손이 택배사 시스템상 확인된 건은 배송 보류 후 송화인에게 먼저 공유하고 처리 방향을 확인해야 하며, 이미 배송이 진행되었거나 회수가 어려운 경우에는 고객에게 회수나 내품 사진을 다시 요구하기보다 택배사 사고 접수 기록과 현장에서 확보 가능한 외부 박스 파손·오염 사진을 기준으로 처리할 수 있도록 논점을 정리했습니다.

이후 택배사 측에서도 표준약관상 사고 발생 시 조치 의무를 인정했고, 내부 검토 후 사고 처리 기준을 재정리했습니다. 그 결과 파손 스캔 등 택배사 시스템상 사고가 확인된 건은 회수·사진 3종 없이 사고접수가 가능해졌고, 스캔이 없는 건도 필요 시 회수하되 외부 박스 파손·오염 사진 등 현장 확인 가능한 증빙을 기준으로 사고접수를 진행할 수 있게 되었습니다.

이를 통해 고객에게 반복적으로 회수와 사진 3종을 요청해야 하는 부담을 줄였고, 배상 회수액은 월 50만 원대에서 745만 원으로 증가했습니다. 같은 기간 매출은 오히려 3분의 1 수준으로 줄었던 것을 감안하면, 이는 매출 증가 효과가 아니라 이전에는 증빙 기준 때문에 제외되던 사고가 실제 배상으로 연결된 결과입니다.

B 물류 운영사 전환 초기 계약서 기반 물류비 차감 기준 정리

물류 운영사 전환 이후에는 사고 발생 건을 단순 요청으로만 전달하면 파트너 회신 지연으로 후속 처리가 멈추고, 책임 귀속이 흐려질 수 있었습니다.

이에 물류 계약서 원문을 먼저 확인해, 상차 이후 발생한 파손·누락·운송 중 사고와 관련 비용 부담이 물류 파트너 책임으로 정리될 수 있는 조항을 확인했습니다. 이를 바탕으로 회사가 먼저 처리한 환불액, 재배송비, CS 보상 비용을 익월 물류비 정산에서 차감 반영할 수 있는 구조로 정리했습니다.

피해 유형, 비용 항목, 정산 확인 기준을 정리해 유관 리더에게 공유했고, 피해 현황 통보서와 정산 참고용 집계 파일을 작성했습니다. 이후 온도대, 주문 단위, 출고 전·출고 후 사고 구분 등 산정 기준을 보완해 실제 물류비 차감 기준으로 운영에 반영했습니다. 이를 통해 약 1,900만 원 규모의 물류비 차감 기준을 정리해 운영에 반영했습니다.

계약서 기준과 정산 반영 가능성을 파트너사에도 명확히 전달한 이후, 사고 확인과 회신 속도가 이전보다 개선되었고 후속 처리 흐름도 안정화되었습니다.

Result

택배사 사고 처리에서는 과도한 회수·고객 증빙 기준으로 막혀 있던 배상 회수 흐름을 실무 증빙 기준으로 재정리해, 배상 회수액을 월 50만 원대에서 745만 원으로 증가시켰습니다.

물류 운영사 전환 이후에는 계약서 원문을 기준으로 책임 조항과 비용 반영 기준을 정리해, 전환 초기의 불안정한 사고 처리 흐름을 빠르게 안정화했습니다.

Case 05

3PL 전환 초기 미출고 후속 처리 자동화 — 재배송 1,151건 주말 선제 대응

Problem

3PL 전환 초기, 물류센터의 출고 준비와 출고 데이터 연계가 안정되지 않아 예정 주문이 대량 미출고됐고, 출고 가능 시점도 확정되지 않은 상황이었습니다. 고객 안내 후 후속 처리 대상은 재배송 1,151건과 취소 777건, 총 1,928건으로 나뉘었습니다.

금요일 오후 이 물량을 전달받았고, 취소 고객에게는 물류센터 전환 이슈를 사과한 뒤 월요일 처리 예정이라고 안내했습니다. 재배송도 원래 월요일에 여러 명이 처리할 계획이었지만, 월요일까지 미루면 하루 출고 가능 주문 한도가 먼저 차서 약속한 출고일을 지키지 못할 위험이 있었습니다.

대량 AS/재배송·반품 처리 시 동일 항목을 반복 입력해야 했고, 처리 건수가 늘어날수록 입력 피로도와 기준값 오류 가능성이 커졌습니다. 특히 귀책 대상, 처리 사유, 보상 기준처럼 후속 정산·집계에 연결되는 값은 한 번 잘못 입력되면 운영 데이터 전체가 왜곡될 수 있었습니다.

또한 상품 문의나 품질 이슈 처리 시 담당 MD와 상품코드를 확인하려면 매번 엑셀이나 별도 자료를 열어야 했고, 반복 조회와 이관 과정에서 처리 시간이 누적됐습니다.

A 주말 선제 대응·자동화 — 반복 입력 항목 7개 → 단축키 1회

주말 동안 자동화를 만들고 재배송 등록을 선제적으로 진행했습니다.

운영 문제와 처리 흐름, 반복 입력값, 사람이 판단해야 할 구간을 먼저 정의했고, Claude의 도움을 받아 Chrome Extension을 구현해 AS/재배송·반품 등록 시 반복 입력되는 주요 항목이 단축키 한 번으로 자동 입력되도록 실제 화면에서 테스트·수정했습니다. 기존에는 주문 확인, 값 입력, 사유 선택, 상태 변경 등 여러 단계를 반복해야 했지만, 반복 입력 구간을 자동화해 반복 입력 항목 최대 7개를 단축키 한 번으로 줄였습니다.

해당 방식으로 AS/재배송 1,151건 이상을 처리했으며, 이후 반복 업무에도 계속 활용하고 있습니다.

다만 모든 단계를 자동화하지는 않았습니다. 귀책 판단, 예외 케이스 확인, 최종 등록처럼 비용·정산·고객 안내에 영향을 주는 구간은 담당자가 직접 확인하도록 남겨 오류 리스크를 낮췄습니다.

B Slack 기반 내부 조회 구조 구축

상품 문의나 품질 이슈 처리 시 담당 MD와 상품코드를 확인하는 과정도 반복적으로 발생했습니다. 기존에는 엑셀이나 별도 자료를 열어 검색해야 했기 때문에, 문의 이관 전 확인 시간이 계속 누적됐습니다.

Slack API와 Apps Script를 활용해 /담당자 슬래시 커맨드 조회 인터페이스를 구축했습니다. 상품명 일부 또는 상품코드를 입력하면 담당 MD와 상품코드가 즉시 조회되고, 결과는 입력자에게만 노출되도록 구성했습니다.

이를 통해 상품 문의 이관 전 내부 조회 동선을 줄이고, 담당자 확인 기준을 팀원들이 동일하게 사용할 수 있도록 정리했습니다.

C AI를 실무 파트너로 활용

Claude, ChatGPT, NotebookLM은 운영 기준 정리, 자동화 로직 설계 보조, 디버깅, 리스크 표현 검토, VOC 분류와 문서 초안 작성에 활용했습니다.

AI가 만든 결과를 그대로 사용하는 방식이 아니라, 실제 정책·원문·운영 데이터와 대조해 검수하는 방식으로 사용했습니다. 이 활용성을 인정받아 AI 도구 사용 비용을 공식 승인받아 실무에 적용했습니다.

Result

반복 입력 항목은 최대 7개에서 단축키 한 번으로 줄였고, AS/재배송 1,151건 이상을 처리하는 데 활용했습니다. 내부 조회 업무는 Slack 명령어 기반으로 전환해 담당 MD·상품코드 확인 동선을 단축했습니다.

주말 동안 실제 처리 속도와 남은 물량을 확인한 뒤, 월요일 지원 계획을 3명에서 2명으로 조정했습니다. 월요일에는 지원 인력 2명과 남은 작업을 오전에 마무리했습니다. 취소는 고객에게 안내한 일정 안에서 처리했고, 재배송은 출고 한도가 차기 전에 선제적으로 등록했습니다.

자동화 대상과 사람의 판단이 필요한 구간을 분리해, 처리 속도뿐 아니라 기준값 일관성과 오류 감소까지 함께 개선했습니다.
